# V1.29 Remote File Manager - Production Checkpoint

This checkpoint is for production-environment verification before the formal V1.29-J release gate.

## Scope

- FTP / explicit FTPS / SFTP / HTTPS WebDAV connection registration and connection test
- Directory navigation/listing, upload/download, mkdir, rename/move, delete, refresh
- Remote -> File Library and File Library -> Remote transfer
- Image/PDF/TXT/CSV preview using the existing File Library validation/preview boundaries
- Owner scope, CSRF, encrypted credentials, bounded transfer, private temporary storage
- SSRF/DNS rebinding controls with public-IP default and administrator CIDR allowlist for private networks

SCP, SMB/NFS, S3/cloud drives, shell command execution, chmod/chown, editor, background sync, archive browsing and public share URLs are not included.

## Required database change

Back up the database first, then apply:

`database/migrations/021_v1_29_remote_connection.sql`

Set `@table_prefix` in the migration to the same prefix as `DB_TABLE_PREFIX` before execution.

## Required private configuration

Generate a dedicated 32-byte Remote File credential key outside the repository. Example:

`php -r "echo base64_encode(random_bytes(32)), PHP_EOL;"`

Use the generated value exactly as printed. `APP_REMOTE_CREDENTIAL_KEY_B64` is not an arbitrary 32/64-character password: strict Base64 decoding must produce exactly 32 bytes (normally the encoded text is 44 characters including padding). Do not hand-type a placeholder/random-looking string.

You can verify the configured value without printing the secret by running `php tools/remote_file_env_check.php`; it must show `[OK] Remote credential key (base64 -> 32 bytes)`.

Configure at least:

- `APP_REMOTE_CREDENTIAL_KEY_ID=primary`
- `APP_REMOTE_CREDENTIAL_KEY_B64=<generated base64 key>`
- `APP_REMOTE_ALLOWED_PORTS=21,22,443` (add only ports actually required)
- `APP_REMOTE_TEMP_DIR=<private writable directory outside public/>`
- `APP_REMOTE_SSH_KNOWN_HOSTS_FILE=<verified known_hosts file>` when SFTP is used

Do not commit `config/local.php`, `.env`, the credential key, private keys, passwords or known_hosts contents containing environment-specific data.

## Private network policy

Private/LAN targets are denied by default. To use a NAS/LAN server, configure both:

- `APP_REMOTE_PRIVATE_NETWORK_ENABLED=true`
- `APP_REMOTE_PRIVATE_NETWORK_CIDRS=<minimum required CIDRs>`

Then enable Private Network only on the individual connection that needs it. Loopback, link-local and other blocked address classes remain denied.

Prefer narrow CIDRs such as `192.168.10.0/24` rather than broad RFC1918 ranges.

## Base Path and symbolic links

The application normalizes every requested path against the configured Base Path and rejects traversal segments. It also refuses listed `symlink`/unknown path components before file operations when the protocol/server exposes that information.

FTP/SFTP servers do not expose symbolic-link metadata uniformly in every listing mode. For those protocols, use a dedicated account whose server-side root/chroot is restricted to the intended tree. Treat the server-side jail/root as the final boundary; do not rely on Base Path alone as a substitute for SFTP chroot or an equivalent FTP server restriction. The UI intentionally offers no operations for entries identified as symbolic links.

## PHP/runtime requirements

Run:

`php tools/remote_file_env_check.php`

Confirm the protocol support required by the production server:

- FTP/FTPS: cURL `ftp`
- SFTP: cURL `sftp`, `CURLOPT_SSH_KNOWNHOSTS`, and a verified known_hosts file
- WebDAV: cURL `https` plus SimpleXML
- Credential storage: Sodium
- FTPS/WebDAV TLS: OpenSSL/cURL TLS support

The application transfer default is 100 MiB, but PHP/Web Server limits can be lower. Check `upload_max_filesize`, `post_max_size`, request-body limits and execution/proxy timeouts before testing large transfers.

## SFTP host-key verification

SFTP is fail-closed when the configured known_hosts file is unavailable. Populate known_hosts from a host key/fingerprint verified through a trusted channel. Do not treat an unverified first network response as sufficient identity proof.

## Recommended production verification

Use a non-critical test directory inside each connection's Base Path.

1. Open `/remote-files` and create one connection.
2. Run Connection Test.
3. Confirm root/Base Path listing.
4. Create a test directory.
5. Upload a small TXT file.
6. Refresh and confirm size/update information.
7. Preview TXT and download it; compare the content/hash locally.
8. Rename the file.
9. Move it to a child directory if available.
10. Save the remote file to File Library and confirm File Library preview/download.
11. Send a File Library file back to Remote and confirm the content/hash.
12. Delete only the test files/directories created for this verification.
13. Repeat for each protocol actually used in production.

For FTPS/WebDAV, also verify that an invalid/untrusted certificate is rejected. For SFTP, verify that a mismatched host key is rejected. For private-network targets, confirm a host outside the configured CIDR is denied.

## Checkpoint release boundary

This checkpoint is not the formal `v1.29.0` release. After production protocol verification, V1.29-J runs the final full regression/package/release gate and only then updates `main`, tag and GitHub Release.
