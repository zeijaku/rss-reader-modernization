# V1.30 Remote Text Editor Design / Security Contract

Status: V1.30-A

Baseline: `v1.29.0` (`b6a3039f6af003f247640d7926ffffab548b825e`)

Feature branch: `feature/v1.30-remote-text-editor`

## Purpose

V1.30 adds a small browser-based Remote Text Editor on top of the V1.29 Remote File Manager. It is not an IDE and does not add a shell, terminal, Git client, binary editor or collaborative editing.

V1.30-A freezes the architecture and security boundaries before read/save implementation begins.

## Existing V1.29 boundaries to reuse

The editor must reuse the existing `app/remote_file/` architecture instead of introducing protocol-specific editor code.

Expected flow:

`Remote Files UI -> Editor page/API -> Remote Service -> RemoteFileProvider -> FTP/FTPS/SFTP/WebDAV`

The existing owner-scoped connection lookup, encrypted credential handling, host validation, private-network policy, Base Path confinement, bounded transfer handling and provider implementations remain authoritative.

`RemoteFileProvider` remains protocol-oriented (`list`, `download`, `upload`, `move`, `delete`, etc.). V1.30 must not add `editText`, `saveText` or similar editor-specific methods to individual protocol providers.

## Initial editable extensions

The initial allowlist is:

- `.txt`
- `.md`
- `.csv`
- `.json`
- `.xml`
- `.html`
- `.htm`
- `.css`
- `.js`
- `.php`
- `.ini`
- `.conf`
- `.yml`
- `.yaml`

Extension is only the first eligibility gate. Content validation is still required before edit mode is allowed.

Binary formats, images, PDF, Office files, archives, executables, database files, video and audio are not editable in V1.30.

## Size contract

`APP_REMOTE_EDITOR_MAX_BYTES` defaults to `524288` bytes (512 KiB).

The editor limit is independent from the much larger general Remote File Manager transfer ceiling. Implementations must enforce the editor limit while downloading/opening and while accepting save content; listing metadata alone is not trusted as the final size authority.

Configuration is clamped to a deliberately small range by `remote_bootstrap.php`.

## Encoding and binary detection

V1.30 initial editing is UTF-8 only.

Opening must fail safely when content is not valid UTF-8. V1.30 does not silently convert Shift_JIS, EUC-JP or other legacy encodings.

At minimum, content validation must reject NUL bytes and unsafe binary/control patterns in addition to checking the extension. A UTF-8 BOM may be recognized and preserved.

## Line endings

LF and CRLF should be preserved when they can be detected safely.

The browser editor may normalize line endings internally; therefore the save path must explicitly reconstruct the original EOL form where supported.

Mixed line endings are not silently normalized in the initial implementation. Until a dedicated policy is implemented, mixed-EOL content should fail safe or remain read-only.

## Path and symlink safety

Editor paths are always connection-relative paths and must pass the existing `remote_path_normalize_relative()` and Remote Service safety checks.

The editor must not implement a parallel path parser.

Traversal, encoded/decoded `..` segments, NUL/control characters, unsafe backslashes and Base Path escape remain rejected.

Open and save must both use the existing symlink/unknown-entry fail-closed checks where provider metadata allows them. A save must re-check the path immediately before mutation instead of trusting only the earlier open result.

Protocol metadata is not uniform and no application-only check can replace a properly rooted/chrooted remote account. V1.30 must not claim otherwise.

## Authentication / credentials / CSRF

All editor operations require the existing authenticated session and owner scope.

Remote credentials are decrypted only server-side through the existing Remote Service provider construction. Credential plaintext, credential envelopes, `APP_REMOTE_CREDENTIAL_KEY_B64`, private keys and `known_hosts` content must not be returned to the browser.

Save is a mutating operation and requires CSRF validation.

Editor content may contain passwords, API keys or source secrets. File content must not be written to normal application logs, exception messages or browser diagnostics.

## Read design

The read path will use the shared Remote Service and bounded provider `download()` flow.

The editor must not load a remote file without enforcing `APP_REMOTE_EDITOR_MAX_BYTES` during the transfer itself.

After bounded download, content eligibility checks produce editor metadata such as UTF-8 validity, BOM state, EOL type, byte size and SHA-256 content hash.

## Conflict detection

V1.30 uses optimistic conflict detection rather than remote locking.

Common cross-protocol baseline:

1. Open downloads the bounded file and calculates SHA-256 hash A.
2. The browser edits the returned text and retains A as an opaque expected-state token/value.
3. Save re-downloads the current remote file under the same editor limit and calculates SHA-256 hash B.
4. Save proceeds only when A equals B.
5. A mismatch returns a conflict response and does not overwrite the remote file.

This catches content changes even when file size and modified time are unchanged.

Provider-specific ETag support may be considered later, but V1.30 does not require widening the provider interface solely for WebDAV.

Optimistic comparison does not eliminate the very small race between the final comparison and the actual remote write. V1.30 must not describe this as file locking.

## Save design

Save must remain above the common `RemoteFileProvider` interface and must not branch into protocol-specific editor code.

A staged strategy is preferred where practical:

1. validate request/content/path;
2. re-download and compare the expected SHA-256 state;
3. upload edited bytes to a bounded temporary sibling path;
4. replace/move the staged file to the original path through the provider `move()` operation;
5. clean up the staged file when a failure occurs where possible.

FTP RNFR/RNTO, SFTP rename and WebDAV MOVE do not provide one universal cross-server atomicity guarantee. Documentation and UI must therefore use wording such as staged/safe save and must not promise an atomic replace across all protocols.

The existing service currently rejects a zero-byte general upload even though provider implementations accept a zero-length stream. V1.30-B/D must explicitly decide and test whether clearing a text file to zero bytes is supported through a narrowly scoped editor save path rather than relaxing unrelated transfer validation accidentally.

## UI decision

Use a dedicated editor page rather than expanding the V1.29 Preview modal.

Reasons:

- better smartphone viewport/keyboard behavior;
- easier dirty-state navigation protection;
- clearer separation between read-only Preview and mutation-capable Edit;
- simpler future replacement of the textarea without changing the Remote Files page structure.

Initial editor control is a normal `<textarea>`. Monaco, CodeMirror, syntax highlighting, autocomplete and IDE features are outside V1.30.

Normal saves do not need a confirmation dialog every time. A dirty-page navigation warning and a clear external-change/conflict warning are preferred.

## Database decision

V1.30 Remote Text Editor requires no database migration.

The existing V1.29 `remote_connection` table remains unchanged. V1.30 does not add editor preferences, edit history, file versions, locks or automatic backup generation tables.

## API boundary

A dedicated editor endpoint is preferred over pushing editor text through the generic API route. The 512 KiB raw content ceiling can grow materially when serialized/escaped, and a dedicated endpoint permits explicit editor request limits and response headers without weakening the generic API limit.

Open and save may share one dedicated endpoint if the methods/actions remain clear, or use separate read/save endpoints if that stays closer to the existing project style. This is finalized in V1.30-B/D after implementation-level review.

## Logging / response handling

- `Cache-Control: no-store` / existing private response headers remain required.
- Dynamic source text is assigned as text/textarea value, never injected as HTML.
- Error responses use stable codes and generic messages; source content and credentials are not echoed into errors.
- Save conflict should return a dedicated conflict status/code (HTTP 409 is the primary candidate).

## Out of scope for V1.30

- Monaco Editor / CodeMirror / IDE conversion
- syntax highlighting / autocomplete / formatter / linting
- SSH terminal / shell command execution
- chmod / chown
- Git client / commit / diff UI
- multi-tab editor
- remote full-text search
- file locking server
- edit history / automatic backup generations
- collaborative editing
- binary / hex / ZIP / Office / image editor
- scheduled/background sync
- SMB / NFS / S3 / additional cloud drives
- automatic Shift_JIS/EUC-JP conversion

## Phase plan

- V1.30-A: Audit / Architecture / Security Contract
- V1.30-B: Text validation / bounded read backend
- V1.30-C: Dedicated editor UI
- V1.30-D: Save backend / optimistic conflict handling
- V1.30-E: Conflict UX / EOL round-trip
- V1.30-F: Security hardening / mobile / protocol verification
- V1.30-G: Production checkpoint and package
- V1.30-H: Full regression / final release

## Test policy

Development phases use focused tests for changed code, security invariants, syntax and required compatibility only.

`tests/run-current.sh` and `tests/run-current-features.sh` are reserved for V1.30-H unless a foundational change explicitly requires broader regression earlier.
