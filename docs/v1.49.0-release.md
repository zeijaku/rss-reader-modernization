# V1.49.0 正式版：更新・確認・復旧手順

> **正式化準備資料**です。本書の作成やDraft PRのCI成功だけでは正式Release・タグは公開されません。正式化の最終承認後にのみ `main` へのマージとGitHub Release手順を進めます。

## 変更概要

V1.48.0のRemote Files正式版からの更新です。DashboardのFeed表示・取得・Search Feedと、Article Actionsのメニュー、記事共有、Stock、Task、Reader Modeを小さなJSモジュールへ分離し、Reader Modeの旧スコープ参照エラーを修正しました。

- Application Version: `1.49.0`
- Asset Revision: `1.49.0`（古い `1.48.0-dev.*` キャッシュからの切り替え）
- Database Migration: **なし**
- 新規必須設定: **なし**
- RSS取得の既定安全サイズ: **2MiBのまま**
- Mail: Composer版ImapEngine 1.25.6および互換依存ライブラリを含むRuntime ZIPが必要

## 公開前の確認

1. CI: PHP 8.1／8.4、Apache 2.4隔離検査、NodeによるDashboard／Article Actions／Reader Mode実行型テスト。
2. 正式化候補PR（`release/v1.49.0-prep`）のRelease-readiness dry-runにて、Runtime / Complete Source ZIP、両SHA-256、manifest/CRC、secret除外、clean-roomを確認する。
3. Runtime ZIPを展開した場所で `vendor/autoload.php` と `DirectoryTree\\ImapEngine\\Mailbox` のロードができることを確認する。
4. Python PlaywrightのCIブラウザテストは環境上スキップされ得る。Dev10段階での手動UI検証済み範囲と未網羅範囲を区別する。
5. 前回までのDraft PRを複数順次マージしない。累積した正式化候補だけをレビューする。

## 配置手順

1. `main` に正式化候補が承認・マージされ、Release Workflowによって `v1.49.0` と正式Runtime ZIP・SHA-256・Artifact Attestationが生成された後に適用する。
2. Runtime ZIPとSHA-256／Attestationを確認し、コード・`public/.htaccess`・`config/local.php`・データベース・アップロード・`var/`・既存`vendor/`をバックアップする。
3. ZIPをアプリケーションルート（`app/`, `public/`, `vendor/` 等が直接存在する階層）に上書きする。既存のプライベート設定・DB・Session・稼働データは削除しない。隠しファイル `.htaccess` も確認する。
4. `vendor/autoload.php` が存在し、Mail Widgetが依存エラーなく起動することを確認する。
5. フッター `RSS Reader Modernization 1.49.0` とJSアセットの `?v=1.49.0` を確認し、ブラウザキャッシュとPHP OPcacheの旧版混在に注意する。

## 基本動作確認

- ログイン／2FA、Dashboard、Feed・Search Feed表示・更新、長いRSS/一時的な取得エラー、Categoryと新着。
- Article Actions開閉・Esc／Tab／矢印キー、PC・スマホのカード内メニュー位置。
- RSS Reader Modeの初回RSS本文、全文取得と閉じる操作、失敗時のRSS本文維持。
- RSS／StockからのURLコピー、X投稿、Stock保存・解除、Task追加（削除・保存の検査にはテスト用データを使用）。
- Calendar、Memo、Mail、Games、Remote Files、File Libraryなど既存機能の基本操作。
- `APP_HTTP_MAX_BYTES` は変更しない。2MiB超のRSSで `response_too_large` による422とカード上の原因表示が出ることは既存仕様。

## ロールバック

問題が生じたら新しい書き込み操作を止め、バックアップしたV1.48.0のコード・`vendor/`・`.htaccess`を一式で戻してください。古い設定・保存データは保持します。V1.49.0でDB Migrationは行わないため、スキーマの巻き戻しは不要です。

## 正式公開の手順

1. このDraft PRのCIと正式パッケージdry-runを成功させ、差分・注意点をレビューする。
2. **別途明示的な最終承認を得て** `main` に正式化候補を一度だけマージする。
3. `main` のCI・Release-readyソースを確認する。
4. 別途明示的にRelease開始を承認した後、共通`.github/workflows/release.yml`を `main` から `1.49.0` で起動する。Release requestファイルによる意図しない起動は避ける。
5. GitHub Release上のRuntime / Complete ZIP、SHA-256・attestationとタグ不変性を検証してからサーバーへ適用する。
