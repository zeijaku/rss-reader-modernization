# Version 1.12-B - RSS Highlight Keyword Backend

Baseline: `rss-reader-modernization-1.12-A-highlight-design.zip`
Checkpoint version: `1.12.0-dev.2`

## Scope

V1.12-B implements the persistence/backend layer for RSS Highlight keywords only.
RSS title rendering and the management UI are intentionally not changed yet.

Implemented:

- new `feed_keyword` table migration;
- new `app/feed_keyword.php` module;
- active keyword list helper for the next UI phase;
- create API: `feed.keyword.create`;
- delete API: `feed.keyword.delete`;
- per-user ownership checks;
- maximum 50 active keywords per user;
- maximum 64 characters per keyword;
- whitespace normalization and case-insensitive duplicate comparison;
- logical delete with `keyword_flag=1`;
- re-registering a deleted equivalent keyword restores the same `keyword_id`.

Not implemented in this checkpoint:

- RSS Highlight management modal;
- keyword JSON handoff to the browser;
- title highlighting;
- Search Feed rendering changes;
- per-keyword colors;
- hide rules / Rules Engine;
- Stock Tag linkage;
- Mail Phase 2.

## Database change

Apply:

`database/migrations/012_v1_12_feed_keywords.sql`

Before applying, set `@table_prefix` to the same value as `DB_TABLE_PREFIX` in `config/local.php`.
The migration creates only the new prefixed `feed_keyword` table and does not modify existing RSS, Stock, Stock Tag, or Mail rows.

Logical columns:

- `keyword_id`
- `keyword_date`
- `keyword_updated_at`
- `keyword_flag`
- `keyword_owner`
- `keyword_value`

The unique key is `(keyword_owner, keyword_value)` and the table uses `utf8mb4_unicode_ci`.

## Backend behavior

### Create

`feed_keyword_create()` validates and normalizes a keyword before writing it.

- empty / invalid UTF-8 / control-character input is rejected;
- repeated whitespace becomes one space;
- values over 64 characters are rejected;
- an already active case-insensitive equivalent keyword is returned without creating another row;
- an inactive equivalent keyword is restored and keeps the previous `keyword_id`;
- a 51st active keyword is rejected.

Writes lock the active owner row while changing keyword state on MySQL. This keeps the per-user count check and duplicate handling serialized without adding a larger transaction framework.

### Delete

`feed_keyword_delete()` is owner-scoped and performs a logical delete:

`keyword_flag = 1`

A user cannot delete another user's keyword. Unknown / foreign keyword IDs are exposed by the API as `404 not_found`.

## API

### `feed.keyword.create`

Input:

- `keyword_value`

Success:

- `201` when a new or previously deleted keyword becomes active;
- `200` when an equivalent active keyword already exists.

The returned keyword object includes:

- `keyword_id`
- `keyword_value`
- `created`
- `restored`

### `feed.keyword.delete`

Input:

- `keyword_id`

Success: `200`

Unknown / non-owned keyword: `404`

Existing public API authentication and CSRF validation are unchanged and continue to be enforced before `api_dispatch()`.

## Focused tests performed

Changed PHP files were syntax-checked with PHP 8.4.

Backend behavior was exercised with a PDO-compatible in-memory test double because this build environment has no PDO database drivers installed.

Confirmed:

- whitespace normalization;
- empty keyword rejection;
- 65-character keyword rejection;
- HTML-looking keyword remains data rather than being specially interpreted;
- first create;
- case-insensitive duplicate handling;
- Japanese keyword handling;
- active list behavior;
- owner A / owner B delete isolation;
- logical delete;
- deleted keyword restoration using the same ID;
- 50 keyword limit;
- API `201` create;
- API duplicate `200`;
- API foreign-owner delete `404`;
- API invalid value `422`.

The MySQL migration itself was not executed in this environment because no database service / PDO driver is available. It was statically checked and should be executed on the target environment before V1.12-C is tested.
