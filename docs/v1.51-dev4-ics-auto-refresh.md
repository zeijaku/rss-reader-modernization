# v1.51.0-dev.4 — ICS購読 第3工程（自動更新・キャッシュ運用）

## 実装内容
v1.51.0-dev.3（ICS解析・月/週/日表示）の上に重ねる更新です。既存DB、ICS秘密URLとSSL/SSRF対策を維持し、新しいDB Migrationはありません。

- **ICS自動更新期限は30分（ソースごと）**。Calendarカードの初回表示、3分おきの期限チェック、タブ復帰時にサーバーへ確認。30分以上経過したものだけICSを再取得します。
- **Calendarの「更新」ボタン**は表示データ更新に先立ってICSの手動取得も試行します。同一ソースの最短取得間隔は60秒。ICS管理の「今すぐ取得」も同じ制限です。
- ICS本文が前回から変化した場合、Calendarの再読み込みを通知。削除した予定が最新ICSから消えた場合はCalendar表示からも消えます。
- 1回のPHP API呼び出しで外部サイトへアクセスするのは最大1件、JSが最大10件の購読を順次処理。通常のCalendar range APIで外部ネットワーク通信は行いません。
- 取得エラー時は最後の正常キャッシュを維持し、管理画面に取得失敗と「前回の予定を表示中」を表示。失敗時も次の自動取得は30分後以降で、3分ごとの連続再試行はしません。
- APIは取得件数／変更件数／失敗件数などだけを返し、ICS秘密URLのpath/query・トークン・本文は返しません。

## 実行環境・制約
今回はcron等のサーバー常駐ジョブを追加しません。**RSS Readerの画面が開いている間に期限を確認するアクセス連動型**です。タブ／画面を閉じている間に30分ごと実行されることはなく、再表示時に期限切れなら取得します。
Google/Outlook側のICS配信の反映遅延はRSS Readerから短縮できません。配信元ICSに旧予定が残る間は再取得しても表示が変わらない場合があります。
RRULEやタイムゾーンの対応制限はDev3に準拠。通常Calendarの編集・保存処理は変更しません。

## 更新用ZIPの適用
対象は既に **v1.51.0-dev.3** が導入済みの環境です。更新前にコード・DBをバックアップし、ZIPのパスを維持して上書きしてください。追加SQLなし。
実行時変更対象の6ファイル：app/version.php、app/calendar_ics.php、app/view/dashboard_modals.php、public/calendar_source_api.php、public/js/calendar-ics.js、public/js/calendar-core.js。
既存ics_rawと購読URL、最後の取得日時を維持してください。

## 動作確認
1. Calendarを表示し、30分を経過した購読先のICSが自動取得されることを確認。
2. Googleで追加／変更／削除した予定について、前回取得から60秒以上後にCalendarの「更新」を押し、配信済みの変更が反映されることを確認。
3. 30分以内の再表示では自動取得されず、3分周期のチェックで過剰な通信が起きないこと。
4. ネットワーク／取得先の障害時にも既存予定を維持し、ICS管理で「取得失敗（前回の予定を表示中）」と示されること。
5. ICS複数件、ユーザー分離、通常Calendar CRUD、繰り返し、月・週・日、フィルター、CSRF、スマートフォンとPCを確認。
