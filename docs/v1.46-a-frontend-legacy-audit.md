# V1.46-A Frontend Legacy Audit

Audit basis: `main` at `d2b44178962f01e672ddc9839338918a48a4eaa2` (V1.45.0).

This phase is intentionally documentation-first. No runtime behavior, security boundary, API contract, application version, or asset revision is changed.

## 2. jQuery dependency scale

The largest concentrations confirmed in the current source are:

- `public/js/dashboard.js`: about 3,591 lines; 338 `$()` matches, 88 `.on()` matches, 407 `var` declarations, and 111 function-IIFE style matches.
- `public/js/calendar-core.js`: about 1,157 lines; 114 `$()`, 23 `.on()`, 2 `$.ajax()`, and 172 `var` declarations.
- `public/js/mail-widget.js`: about 1,597 lines; 314 `$()`, 39 `.on()`, 2 `$.ajax()`, and 212 `var` declarations.
- `public/js/rss-management.js`: still strongly jQuery-oriented.
- `public/js/account-2fa.js`: still uses multiple `$.ajax()` calls.

jQuery is therefore still a real runtime dependency, not just a small compatibility shim. Removing it globally in V1.46 would create unnecessary regression risk.

## 4. window.* and global coupling

The current frontend uses globals intentionally as a lightweight integration mechanism.

Examples include:

- `window.IGuguruDashboardCore`
- `window.RssAllRecent`
- `window.SearchFeedOwnedCategory`
- Calendar globals such as `window.iGuguruCalendarViews`, `window.iGuguruCalendarSources`, etc.
- game/widget globals

This means file order is part of the runtime contract.

The current `public/index.php` loads `dashboard-core.js` before `dashboard.js`, then loads follow-on scripts. Calendar is bootstrapped separately through `calendar.js`.

V1.46 should reduce unnecessary globals when a module is being safely separated, but should not globally replace the existing namespace/load-order model in one release.

## 5. var / IIFE and other legacy patterns

Legacy patterns are widespread:

- `var` is dominant in older files.
- many files are wrapped in `(function (...) { ... })(...)` IIFEs.
- common browser objects are passed through IIFE parameters.
- globals are often deliberately exposed through `window.*`.

These patterns are old but currently stable. Conversion to `let`/`const`, classes, modules, or arrow functions must not be done as cosmetic repository-wide churn.

Recommendation: modern syntax only when touching an extracted, independently testable unit.

## 6. Relatively modern areas already using browser APIs

Several areas already demonstrate a safer migration style:

- `public/js/remote-files.js` uses `fetch()` and multiple `addEventListener()` bindings without `$()`.
- `public/js/file-library-core.js` uses `fetch()` and native event listeners.
- `public/js/all-rss-recent.js` already uses native event listeners in parts of its UI.
- `public/js/search-feed-owned-category.js` has minimal jQuery-style coupling compared with the older dashboard core.

These files should be used as style references for V1.46-C rather than introducing a new frontend framework.

## 7. Script loading and cache contract

`public/index.php` uses `app_asset_url(...)` for static entry scripts.

`public/js/calendar.js` is itself a revision-aware loader. It reads the `v=` value from its own script URL and propagates the same revision to dynamically loaded Calendar/Mail/Camera/Widget scripts and styles. It also serializes script loading with `async = false`, maintains a queue, and retries failed asset loads.

This is a critical compatibility mechanism.

V1.46-B must preserve:

1. `APP_ASSET_REVISION` propagation,
2. deterministic script order,
3. retry behavior where applicable,
4. no unversioned dynamic child asset,
5. no newly extracted dashboard file that can be cached independently without the current revision.

Recommended B implementation: newly extracted dashboard files should be direct `app_asset_url()` entries or be loaded by one revision-aware dashboard entry loader. Do not hard-code release numbers in individual JS filenames or query strings.

## 9. Dependency update candidates

### Bootstrap / Bootswatch

Current 5.3.8 is already the current Bootstrap 5.3 release as of this audit. No V1.46 update is recommended.

### jQuery

jQuery 4.0.0 is available and is the current major branch. However, this application still has substantial jQuery usage including Ajax and event handling.

Recommendation: do not combine the 3.7.1 -> 4.x major upgrade with the B extraction work. Reassess in D after C has reduced the highest-risk usage. If attempted, use the full build, not slim, unless all Ajax/effects requirements are independently removed and tested.

### Font Awesome

Font Awesome 7.x is available, while 6.7.2 remains an LTS line. Version 7 includes visual/layout behavior changes, including fixed-width behavior changes.

Recommendation: keep 6.7.2 in V1.46 unless there is a concrete feature/security reason to upgrade. An icon-library major upgrade offers little modernization value compared with the visual-regression risk.

### hls.js

Current application pins 1.6.16. Newer 1.6 maintenance releases and 1.7.x exist.

Recommendation: D may update hls.js, preferably as an isolated change with SRI, lazy-load, native-HLS fallback, playback, retry, iOS/Safari/Chromium behavior, and CSP/network tests. Do not bundle it with jQuery or Font Awesome changes.

## 10. Parts that should be fixed first

Priority candidates for B:

1. Extract Dashboard Task + task-item CRUD.
2. Extract Memo CRUD.
3. Extract Clock CRUD.
4. Extract Game widget CRUD.
5. Extract Search Feed CRUD/refresh if current Search Feed tests remain green.
6. Consider article actions / Reader helpers after the smaller CRUD groups.

Why these first:

- responsibilities are already visibly grouped by forms/selectors;
- they have narrower API boundaries than feed rendering and D&D;
- they can be contract-tested against existing selectors and payload fields;
- extraction reduces dashboard.js without first changing transport technology.

The first B changes should be relocation with behavior preservation, not simultaneous jQuery-to-native conversion.

## 11. Parts better left untouched initially

Do not start B/C with:

- Dashboard widget D&D / pointer / keyboard reorder logic.
- feed rendering and refresh/error state machine.
- Calendar core / recurrence / occurrence / partial-refresh chain.
- Mail widget main flow.
- asset loader/retry logic in `calendar.js`.
- Bootstrap modal/offcanvas integration.
- Account Security / 2FA Ajax flows.
- security boundary or API payload shapes.

These are either highly stateful, highly interconnected, security-sensitive, or strongly dependent on load order.

## 12. Recommended V1.46-B scope

B should be a conservative extraction phase.

Suggested target files:

- new `public/js/dashboard-task.js`
- new `public/js/dashboard-memo.js`
- new `public/js/dashboard-clock.js`
- new `public/js/dashboard-game.js`
- optionally `public/js/dashboard-search-feed.js` after the first four are proven stable
- `public/js/dashboard.js`
- `public/index.php` or a revision-aware dashboard loader
- Current tests for load order, selectors, payloads and asset revision

Keep the existing DOM and API contracts unchanged.

Do not introduce ES Modules in B.

## 13. Recommended V1.46-C scope

After B has stable module boundaries:

- convert extracted files individually from jQuery event registration to native listeners where this reduces coupling;
- use `fetch` only where request/response semantics can exactly match the current helper contract;
- prefer shared existing CSRF/error helpers over duplicated fetch wrappers;
- keep jQuery in Calendar, Mail, RSS Management, Account Security and any complex Dashboard area where removal would increase code/risk;
- convert `var` to `let`/`const` only in files already being materially modernized.

Success criterion should be lower coupling and better testability, not a target percentage of jQuery removal.

## 14. Recommended V1.46-D scope

- hls.js isolated update evaluation.
- dependency docs / notices alignment after any accepted dependency update.
- no Bootstrap/Bootswatch update unless upstream moves beyond the current 5.3.8 and there is a specific reason.
- keep Font Awesome 6.7.2 unless a concrete benefit justifies v7 visual regression.
- evaluate jQuery 4 only after C and only in a dedicated sub-step.
- consolidate Calendar polish/override CSS only after selector provenance and visual tests are added.
- consolidate/remove generation-named Drawer CSS only after confirming active loader references and theme/mobile behavior.

## 15. Risks

High:

- browser cache mismatch between updated HTML and stale extracted scripts;
- load-order breakage from global namespace dependencies;
- selector drift in delegated events;
- changed form serialization / Ajax payload behavior;
- Modal lifecycle/focus regressions;
- D&D and Resize behavior regression on desktop or touch;
- Calendar CSS cascade changes;
- jQuery 4 behavioral incompatibility in legacy plugins/patterns;
- Font Awesome 7 icon sizing/layout changes.

Medium:

- duplicated event binding after extraction;
- multiple initialization paths executing the same feature twice;
- race conditions introduced by dynamic loading;
- theme-specific CSS regressions;
- smartphone-only interaction regressions.

## 18. Decision

The original A/B/C/D plan remains appropriate, with two refinements:

- B should be narrower than a generic "dashboard.js split": first extract four low-to-medium coupling CRUD domains without changing their transport/event technology.
- D should not be treated as a mandatory dependency-upgrade phase. Bootstrap and Font Awesome should likely remain unchanged; hls.js is the strongest update candidate; jQuery 4 is conditional on C results.

No runtime change is required in V1.46-A.
