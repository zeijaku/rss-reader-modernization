# Version 1.12-A - RSS Highlight Design / Impact Review

Baseline: `rss-reader-modernization-1.11.0-stock-tags.zip`
Checkpoint version: `1.12.0-dev.1`

## 1. Scope

V1.12-A is a design-only checkpoint for RSS keyword highlighting.
No RSS fetch behavior, Search Feed matching behavior, Stock behavior, Mail behavior, or user data is changed in this checkpoint.

Target behavior for later implementation:

- A user can register highlight keywords.
- Only matching substrings inside RSS article titles are highlighted.
- Multiple keywords can match one title.
- Both normal RSS Widgets and Search Feed results use the same highlight behavior.
- The first implementation uses one common highlight color.
- The design keeps room for later hide rules and Stock Tag linkage without introducing a Rules Engine now.

## 2. Current rendering path confirmed from V1.11

Normal RSS:

`feed.fetch` -> `api_feed_fetch()` -> `api_safe_feed_payload()` -> `public/js/dashboard.js::renderFeedItems()`

Search Feed:

`widget.search.fetch` -> `search_feed_execute()` -> `api_safe_feed_payload()` -> `public/js/dashboard.js::renderFeedItems()`

Both paths converge on `renderFeedItems()`. Therefore the title decoration can be implemented once in the shared client-side renderer.

Current title insertion uses jQuery `.text()`. This is important XSS protection and must not be replaced by raw `.html()` when highlighting is implemented.

## 3. Recommended persistence design

A database change is required for the recommended implementation.

Reason:

- Highlight settings should follow the user across browsers/devices.
- Browser localStorage would avoid a migration but would make settings device-local.
- Future hide rules / Stock Tag linkage need a stable user-owned keyword entity.
- Adding a dedicated table avoids growing the legacy `user_conf` row with encoded keyword lists.

Recommended new logical table: `feed_keyword`

Proposed columns:

- `keyword_id` BIGINT UNSIGNED AUTO_INCREMENT
- `keyword_date` DATETIME NOT NULL
- `keyword_updated_at` DATETIME NOT NULL
- `keyword_flag` TINYINT UNSIGNED NOT NULL DEFAULT 0
- `keyword_owner` INT UNSIGNED NOT NULL
- `keyword_value` VARCHAR(64) NOT NULL

Recommended keys:

- PRIMARY KEY (`keyword_id`)
- UNIQUE (`keyword_owner`, `keyword_value`)
- INDEX (`keyword_owner`, `keyword_flag`, `keyword_value`)

The table stores keyword entities only. V1.12 should not add rule/action columns yet. A later version can attach rule metadata or Stock Tag relations separately if needed.

Planned migration name: `database/migrations/012_v1_12_feed_keywords.sql`

Existing rows/tables do not need to be rewritten.

## 4. Keyword validation / matching policy

Initial recommended limits:

- up to 50 active keywords per user
- maximum keyword length: 64 characters
- trim leading/trailing whitespace
- collapse repeated internal whitespace
- reject empty strings
- case-insensitive matching
- substring matching; word-boundary-only behavior is not used

Examples:

- keyword `OpenAI` matches `OpenAIがPHP対策を強化`
- keyword `PHP` matches the `PHP` portion in the same title
- keyword `PHP` also matches `PHP8`

Overlapping keywords should not generate nested markup. Longer matches should take priority when ranges overlap. Example: with `OpenAI` and `AI`, the visible `OpenAI` portion is highlighted once.

## 5. Rendering design

Add a small shared JavaScript helper used by `renderFeedItems()`.

The helper must:

1. receive the original plain title and the active keyword list;
2. find case-insensitive matches;
3. create plain text nodes for unmatched sections;
4. create a `<mark class="feed-keyword-highlight">` element for matched sections;
5. never insert the feed title or keyword with `innerHTML` / jQuery `.html()`.

The original title remains unchanged in:

- `data-full-title` for the truncation tooltip;
- article Actions `data-article-title`;
- the in-memory item record used by Stock / Task actions;
- API payloads and Search Feed matching.

Highlighting is display-only.

## 6. Client keyword state

Recommended initial-page handoff:

- PHP reads the current user's active keywords once.
- `public/index.php` emits a safe `application/json` payload containing keyword IDs and values.
- JSON output uses the existing escaped/safe output policy (including JSON hex escaping where appropriate).
- `dashboard.js` parses that payload into a small in-memory keyword list.

This avoids returning the same keyword list with every RSS fetch and every Search Feed fetch.

After keyword create/delete, JavaScript can update the in-memory list and re-render currently visible `.feed-item-title-text` elements from their existing `data-full-title` value. A full page reload is not required.

## 7. Management UI

Recommended location: a new global `RSS Highlight` item in the existing drawer settings area.

It opens a Bootstrap 4 modal containing:

- one keyword input;
- Add button;
- current keyword chips/list;
- Remove action per keyword;
- current count / maximum count.

Initial version does not need per-keyword colors, priorities, scopes, regex, include/exclude selectors, or a Rules Engine.

## 8. Backend/API impact

Recommended new PHP module:

- `app/feed_keyword.php`

Recommended functions:

- validate / comparison helper
- list active keywords owned by user
- create keyword
- delete keyword owned by user

Recommended API actions:

- `feed.keyword.create`
- `feed.keyword.delete`

A separate list action is optional because the initial page already receives the current list. It can be added later if asynchronous list refresh becomes useful.

`app/bootstrap.php` will include the new module.
`app/common/common_conf.php` will add `feed_keyword` to the known-table allowlist.

## 9. CSS impact

Add only a small rule to `public/css/dashboard.css`, for example through `.feed-keyword-highlight`.

Requirements:

- common color for all keywords in V1.12;
- inherit title text color;
- no layout-breaking display mode;
- preserve the existing two-line clamp/truncation behavior;
- preserve NEW bell positioning and title tooltip behavior.

## 10. Security / compatibility constraints

Must preserve:

- user ownership checks for all keyword writes;
- CSRF behavior already used by the JSON API;
- no raw HTML rendering from feed titles or keyword values;
- no change to RSS SSRF / redirect policy;
- no change to feed cache semantics;
- no change to Search Feed filtering semantics;
- no change to Stock data or Stock Tag data;
- no Mail changes during RSS Highlight phases.

## 11. Focused test plan

Do not run the full historical regression set for every checkpoint.

### Backend / migration

- migration creates only the new keyword table;
- rerun safety if the migration uses `CREATE TABLE IF NOT EXISTS`;
- owner A cannot delete owner B keyword;
- duplicate keyword handling;
- empty / too-long keyword rejection;
- max keyword count rejection.

### Rendering

- no keyword -> original title unchanged;
- one keyword -> exact substring highlighted;
- multiple keywords -> all non-overlapping matches highlighted;
- same keyword repeated in one title -> all occurrences highlighted;
- ASCII case-insensitive match;
- Japanese keyword match;
- regex metacharacters in a keyword are treated as literal text;
- overlapping keywords do not produce nested/broken markup;
- HTML-looking title/keyword remains text, not executable markup;
- long titles still clamp to two lines and tooltip still shows the original title;
- NEW bell remains aligned.

### Integration

- normal RSS Widget title highlighting;
- Search Feed result title highlighting;
- Search Feed query matching result set remains unchanged;
- article Actions still receive the original title;
- Stock saved title remains the original title;
- add/delete keyword updates visible titles without requiring feed refetch.
