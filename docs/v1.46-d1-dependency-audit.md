# V1.46-D1 Dependency Audit

Audit date: 2026-10-08

## Purpose

V1.46-D1 is an investigation and decision phase only.

No runtime dependency, application behavior, security boundary, APP_VERSION, APP_VERSION_LABEL, APP_ASSET_REVISION, Tag, or GitHub Release is changed in D1.

The goal is to decide which dependency changes should actually be implemented in V1.46-D2 without turning the finishing phase into another broad migration.

## Upstream status checked

### Bootstrap / Bootswatch

Bootstrap's current 5.3 line still lists 5.3.8 as the latest release. Bootswatch v5 is also tuned for Bootstrap 5.3.8.

Sources:
- https://getbootstrap.com/docs/versions/
- https://github.com/twbs/bootstrap
- https://bootswatch.com/
- https://github.com/thomaspark/bootswatch

GitHub's Bootstrap security page currently shows no published security advisories.

Decision: **KEEP 5.3.8**.

Reason:
- already current
- Bootstrap and all seven Bootswatch themes are aligned at the same version
- no security-driven upgrade exists
- no value in replacing equivalent assets during a finishing phase

### jQuery

The current app uses jQuery 3.7.1 full build.

jQuery 4.0.0 was released in January 2026 and is now the current full-support branch. The upstream support policy states that 3.x is critical-only and recommends migration to 4.x.

Sources:
- https://blog.jquery.com/2026/01/17/jquery-4-0-0/
- https://jquery.com/upgrade-guide/4.0/
- https://jquery.com/support/
- https://github.com/jquery/jquery/security

jQuery 4 is not a drop-in replacement for the current application.

The upstream 4.0 upgrade guide removes APIs including:
- jQuery.isArray
- jQuery.isFunction
- jQuery.isNumeric
- jQuery.parseJSON
- jQuery.trim
- jQuery.type
- jQuery.proxy
- other deprecated/undocumented APIs

Current high-jQuery runtime code already contains direct blockers:

- public/js/utility-widgets.js
  - $.isArray at lines 376, 884, 1237, 1565
  - $.trim at line 581
- public/js/clock-timer.js
  - $.isArray at lines 1338, 1675, 1676, 1774
- public/js/connection-monitor.js
  - $.isArray at line 1014

This is **9 direct $.isArray calls + 1 $.trim call** in three major runtime files.

The broader usage surface is still large. A D1 scan of major modules found approximately:
- utility-widgets.js: 400+ direct $() uses
- mail-widget.js: 300+ direct $() uses
- dashboard.js: 200+ direct $() uses
- clock-timer.js: 170+ direct $() uses
- calendar-core.js: 100+ direct $() uses
- connection-monitor.js: 100+ direct $() uses
- camera-video.js: 100+ direct $() uses

jQuery 4 also changes some behavior beyond removed helper APIs, including focus/focusin ordering and CSS numeric-unit handling. Current code includes focus/focusin-dependent behavior in Calendar/Clock-related modules, so a real migration should use jQuery Migrate 4 as a temporary development diagnostic and must receive a separate browser-focused regression pass.

Decision: **KEEP jQuery 3.7.1 in V1.46**.

Rationale:
- no currently published advisory was found that forces an emergency move away from 3.7.1
- 3.x remains eligible for critical fixes
- V1.46-C already reduced direct dependency in Task/Memo/Game/Clock
- forcing 4.0 into D2 would expand the scope from dependency finishing to another broad frontend migration

Future action:
- continue reducing direct jQuery usage
- replace the known $.isArray / $.trim blockers with native APIs as part of a dedicated jQuery 4 readiness phase
- test jQuery 4 + uncompressed jQuery Migrate 4 in development
- remove Migrate before production

### Font Awesome Free

Current: 6.7.2.

Latest checked release: 7.3.1.

Sources:
- https://fontawesome.com/versions
- https://www.npmjs.com/package/@fortawesome/fontawesome-free
- https://docs.fontawesome.com/upgrade/whats-changed/
- https://github.com/FortAwesome/Font-Awesome/security

Font Awesome 7 is a major asset transition. Upstream specifically notes:
- webfonts are now WOFF2-only
- TTF/WOFF webfonts are no longer shipped
- CSS/SCSS were modernized
- backward compatibility is provided for many older icon names, but the asset inventory changes

The current repository has an explicit Font Awesome 6.7.2 inventory contract covering:
- all.css
- Solid / Regular / Brands
- v4 compatibility fonts
- both TTF and WOFF2 files
- icon alias checks
- license inventory

No published Font Awesome security advisory was found that requires an upgrade.

Decision: **KEEP Font Awesome 6.7.2 in V1.46**.

Reason:
- major asset/inventory change
- broad UI icon impact
- low functional benefit to this application
- no security forcing function
- visual regressions are more likely than user-visible benefit

A later dedicated icon cleanup may reconsider v7 after removing obsolete compatibility assets and inventory assumptions.

### hls.js

Current: 1.6.16, loaded only when an HLS Camera / Video Widget requires it.

Current load:
- pinned jsDelivr URL
- exact version check
- Subresource Integrity
- anonymous CORS mode
- lazy loading
- Native HLS fallback when available

Latest checked stable release: **1.7.3**.

Sources:
- https://github.com/video-dev/hls.js/releases
- https://github.com/video-dev/hls.js/security

Upstream states that the 1.6 -> 1.7 transition removes no public exports and requires no runtime behavior change for JavaScript consumers. The current application only relies on stable APIs:
- Hls.isSupported()
- new Hls(...)
- Hls.Events.MANIFEST_PARSED
- Hls.Events.ERROR
- Hls.ErrorTypes.NETWORK_ERROR
- Hls.ErrorTypes.MEDIA_ERROR
- loadSource()
- attachMedia()
- startLoad()
- recoverMediaError()
- destroy()

The hls.js security policy currently supports >=1.6 and lists no published security advisories.

However, releases after 1.6.16 contain relevant playback fixes, including segment-loop, live reload, encrypted low-latency stall, and other streaming reliability fixes.

Decision: **UPDATE to hls.js 1.7.3 in D2**.

Additional D1 recommendation: **vendor hls.js locally instead of continuing the runtime CDN dependency**.

Reasons:
- all other primary frontend runtime libraries are already vendored
- removes the only optional third-party executable JavaScript fetch from normal application runtime
- avoids CDN availability dependency
- simplifies future CSP hardening toward script-src 'self'
- keeps production deployment self-contained
- hls.js is already lazy-loaded, so local vendoring does not require loading it on every page

D2 should:
- add a clearly versioned local minified hls.js runtime asset
- load it through the application's asset revision mechanism
- keep lazy loading and Native HLS fallback
- keep Apache-2.0 notice/license evidence
- replace the old CDN/SRI-specific tests with local artifact hash/version/inventory tests
- run focused HLS behavior tests plus the full regression gate

This is a supply-chain/availability simplification, not an emergency vulnerability response.

### PHPMailer

Current: 7.1.1.

Upstream latest checked release: **7.1.1**.

Sources:
- https://github.com/PHPMailer/PHPMailer/releases
- https://github.com/PHPMailer/PHPMailer/security
- https://github.com/PHPMailer/PHPMailer/blob/master/changelog.md

Decision: **KEEP 7.1.1**.

The application already vendors only the PHPMailer source needed at runtime and does not require Composer on the production server.

Security notes:
- the old advisories documented by PHPMailer affect much older 6.x releases and are not applicable to 7.1.1
- current upstream master has an unreleased changelog item concerning XOAUTH authentication with long tokens potentially reporting success when authentication failed
- this application does use PHPMailer XOAUTH2 for OAuth SMTP, with its own OAuthTokenProvider implementation

There is no newer stable PHPMailer release to install in D2. Therefore:
- do not vendor unreleased master
- keep 7.1.1
- monitor the next PHPMailer stable release and review that XOAUTH fix when released

4. perform the separately planned CSS cleanup/finishing work

### Do not update in V1.46-D2

- Bootswatch 5.3.8

Dependency work:
- hls.js exact artifact/version contract
- local-only runtime loading

- lazy load preserved
- Hls.isSupported path
- Native HLS fallback
- network/media recovery remains bounded

Browser/server verification:
- HLS stream on a browser using hls.js/MSE

## jQuery 4 follow-up gate

A future jQuery 4 phase should not begin until all of the following are true:

1. removed jQuery 4 helpers in application code are eliminated
2. major jQuery-heavy modules have focused browser/runtime coverage
3. a development-only jQuery Migrate 4 pass is clean or understood
4. focus/focusin behavior is regression-tested
5. CSS numeric setter assumptions are audited
6. authentication/CSRF/AJAX error handling is verified against the real jQuery 4 full build
7. Migrate is not present in the production package

## D1 conclusion

V1.46-D1 does **not** justify a broad dependency refresh.

The safest and highest-value D2 dependency change is hls.js only.

That keeps V1.46-D as a finishing phase:
- one low-coupling dependency improvement
- CSS cleanup
- documentation/license cleanup
- final regression and V1.46.0 release preparation

jQuery 4 and Font Awesome 7 should remain separate future migrations rather than being hidden inside V1.46-D.
